# Карточки дерева: обновления и повторный рендер

Локальный этап от 25.11.2026. Основание — согласованная задача улучшить дерево; Jira в этой задаче не используется. Изменение сохраняется отдельной веткой, без публикации текущего этапа на GitHub.

Продолжение от 26.11.2026: проверки настоящего TreeView и исправления камеры/меню описаны в [tree-viewport-interactions.md](tree-viewport-interactions.md). Ограничения ниже относятся к первоначальному этапу карточек.

## Изменения

- Ключ карточки теперь использует `node.id`. Перемещение видимого узла не пересоздаёт карточку и её корневой DOM-элемент из-за новых координат. Внутренние ключи исправлены для полного, pill и micro представлений.
- Сравнение свойств карточки учитывает родителей, братьев/сестёр, связанные состояния сворачивания, сторону боковой ветки, новый узел раскладки и обработчики. Ранее часть этих изменений могла оставаться незаметной для `memo`.
- `useTreeCardActions` передаёт стабильные функции, вызывающие последние обработчики завершённого React commit. Изменение камеры само по себе не меняет ссылки обработчиков. Отсутствие необязательных обработчиков сохраняется, чтобы работал прежний переход к выбору персоны.
- Подключено ранее проверенное исправление кэша из `fix/tree-layout-cache-revisions`: ссылки коллекций и ревизии участвуют в ключе, повторное чтение обновляет LRU, параметры веера учитываются до выбора записи. Ключ повторного чтения не перебирает всех персон.
- Чистые сравнения и типы карточки вынесены из большого компонента. В общий запуск тестов и CI включена проверка дерева.

## Requirements vs Implementation

Ожидания ниже — технические критерии этой согласованной задачи, а не требования Jira.

| Ожидание задачи | Expected | Implementation | Code Reference | Status |
| --- | --- | --- | --- | --- |
| Сохранение карточки при перемещении | Для остающегося видимым узла в том же представлении меняются координаты, сохраняются DOM и фокус | Ключ не содержит координат; содержимое обновляется при новом узле | `TreeView.tsx`; `TreePersonCard.tsx` | MATCH на изолированной странице |
| Актуальные родственники | Изменённые родители и братья/сёстры появляются в уже открытом меню | Сравниваются ссылки родителей и элементы массивов родственников | `treePersonCardMemo.ts`, `areTreePersonCardPropsEqual` | MATCH на синтетических данных |
| Актуальные действия | Стабильная ссылка не удерживает устаревшее действие; необязательное действие сохраняет fallback | Последние завершённые обработчики хранятся в ref, доступность необязательных действий учитывается отдельно | `useTreeCardActions.ts` | MATCH на изолированной странице |
| Повторное использование при движении камеры | Неизменённые карточки пропускают повторный рендер | Стабильные действия и сравнение свойств позволяют `memo` пропускать изменения только камеры | `treePersonCardMemo.ts`; `TreeView.tsx` | MATCH в проверенной фикстуре |
| Актуальная раскладка | Изменение коллекции или ревизии исключает устаревший кэш | Общая ревизия используется кэшем раскладки и индексом связей | `layoutCache.ts`; `treeLayout.ts` | MATCH в модульных тестах |

## Проверки и покрытие

Локально прошли 188 тестов: `npm test` — 148 (sync 29, storage/read/families 55, search 11, tree 38, API 15), отдельно trash 37 и production server 3. `npm run lint` (TypeScript) и `npm run build` прошли. Firestore Emulator повторно в этом UI-этапе не запускался; его результаты относятся к предыдущему этапу стабильности.

| Область | Проверки |
| --- | --- |
| Инвалидация раскладки, веер, LRU и явная очистка | 22 ранее подготовленных теста раскладки |
| Уникальность и сохранение ID при повторных браках и общем предке | 2 теста, вертикальная и горизонтальная раскладки |
| Родители, родственники, их порядок и сворачивание, сторона ветки, счётчики, брак, обработчики, выделение, приватность и LOD | 14 тестов сравнения свойств карточки |
| Реальное обновление меню родителей и родственников | 2 браузерных сценария |
| Сохранение DOM и фокуса при перемещении | 1 браузерный сценарий |
| Последний обработчик и переключение необязательного действия | 2 браузерных сценария |
| 50 изменений камеры и сохранение карточек при перемещении в трёх LOD | 2 браузерных сценария |

В Chromium 153.0.8010.12 через локально установленный Playwright 1.63.0 прошли 7 сценариев на отдельной странице с настоящим `TreePersonCard` и синтетическими 40 карточками. Ошибок страницы и внешних запросов не было. При 50 изменениях только камеры все 40 корневых элементов сохранились; MutationObserver не зарегистрировал внутренних изменений DOM. Локальное время цикла — 96,8 мс. Это не замер FPS и не профиль полной страницы дерева.

Бенчмарк `node --import tsx benchmarks/treeLayoutCache.ts`: 10 000 синтетических персон, 1 000 повторных чтений прогретого кэша, пять серий — 7,11 / 1,62 / 1,64 / 1,53 / 1,49 мс; медиана 1,62 мс. Холодная раскладка, отрисовка и сеть в этот замер не входят.

Браузерная проверка запускается отдельно: `npm run test:tree-browser`. Нужны установленный Playwright и Chromium; если пакет находится вне зависимостей проекта, `PLAYWRIGHT_MODULE` задаёт URL его ES-модуля. `TREE_BROWSER_OUTPUT` задаёт каталог JSON-отчёта и снимка. Проверка блокирует внешние запросы, не импортирует приложение целиком и не подключается к рабочему Firebase.

## Potential defects & technical risks

Подтверждённых дефектов в перечисленных выполненных сценариях не обнаружено. Проверка полного приложения на пользовательском дереве ещё нужна:

1. На полной странице изменить имя родителя и сестры при открытых меню, затем свернуть отдельную боковую ветку; убедиться в актуальности подписей и счётчиков. Изолированный компонент проверен, связка всех обработчиков `TreeView` целиком — нет.
2. На большом дереве проверить перемещение камеры, масштаб, выделение и повторные браки. Виртуализация по-прежнему может удалять карточки вне области видимости; сохранение DOM доказано для карточек, остающихся в отрисованном наборе. FPS полной страницы не измерялся.
3. Данные должны обновляться заменой коллекций/объектов либо явной ревизией или очисткой кэша. Мутация объекта на месте без изменения ревизии не является поддерживаемым способом инвалидировать кэш. Сценарии с явной ревизией проверены.
4. Новый узел раскладки намеренно вызывает обновление карточки целиком: это учитывает все счётчики и данные брака. Полный пересчёт раскладки пока выполняется в основном потоке; Worker в этот этап не входит.

Все проверки использовали синтетические данные или заглушки. Рабочие генеалогические записи не менялись.
