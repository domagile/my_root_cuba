# Быстрое сравнение неизменённых полей персоны

Локальная ветка: perf/person-delta-comparison. База: 3a0e6b7.
Подготовлено 25.11.2026, отдельно от веток меню и кеша дерева.
Jira issue не задан; это оптимизация существующего алгоритма без изменения
состава данных, отправляемых при сохранении.

В computePersonDelta добавлена проверка Object.is до JSON.stringify.
Одинаковые примитивы и общие неизменяемые объекты пропускаются сразу.
Для разных значений сохранено прежнее глубокое сравнение через JSON:
новые, изменённые и удалённые поля продолжают попадать в дельту как раньше.

## Покрытие

9 проверок: неизменённая карточка; одно изменённое поле; общие вложенные поля;
равные вложенные данные в разных объектах; изменённые вложенные данные;
удалённое поле; null/undefined; новая персона; изменение только updatedAt.
Один и тот же набор проходит на исходном и оптимизированном вариантах.
Это проверка совместимости алгоритма для JSON-совместимых данных Person,
а не определение новых бизнес-правил из текущей реализации.

Команды проверки:

```sh
npm run test:delta
npm test
npm run lint
npm run build
npm run bench:delta
```

npm test на этой независимой ветке включает прежние 59 тестов.
Отдельный test:delta добавляет 9 проверок, всего 68 локальных проверок.
Тесты кеша дерева находятся в отдельной ветке и в это число не включены.
Для будущей доставки test:delta добавлен в CI; удалённый workflow из этой
локальной работы не запускался.

## Информационный замер

Синтетическая персона: заметка на 160000 символов, 2000 вложенных полей,
меняется только firstName; остальные данные переиспользуются.
Node.js 24.15.0; 500 сравнений, пять серий после прогрева, медиана:

| Реализация | Время 500 сравнений |
| --- | ---: |
| Исходная | 657,28 мс |
| Оптимизированная | 0,64 мс |

Скрипт benchmarks/personDelta.ts воспроизводит этот узкий замер.
Он не измеряет скорость всего интерфейса или обычной небольшой карточки;
выигрыш зависит от объёма неизменённых данных и способа обновления объектов.

## Potential defects & technical risks

- Прямое изменение вложенного объекта, на который одновременно ссылаются
  prevPerson и nextPerson, не создаёт независимого старого состояния.
  Исходный алгоритм тоже не выявляет такую мутацию. Редактирование должно
  создавать новый вложенный объект. Стендовый сценарий: изменить вложенное
  поле и проверить его после сохранения/перезагрузки.
- Проверки рассчитаны на JSON-совместимые данные карточки. Объекты с
  побочными эффектами в toJSON не являются проверенным входом.
- Внешний Firestore, реальные пользовательские карточки и полный сценарий
  сохранения через браузер в этом изменении не исполнялись.
