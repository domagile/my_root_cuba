# Доступ к Firestore и публичное дерево

Изменение закрывает прямой доступ к полным данным. Применяется к базе
`ai-studio-a567c750-fcc0-4247-9c87-f3613091d667` проекта `smiling-spanner-31ttq`.
Этот файл описывает подготовленные изменения; он не подтверждает развёртывание.

## Политика доступа

| Пользователь | Полные данные | Изменение данных | Whitelist и настройки безопасности |
| --- | --- | --- | --- |
| Без входа, вход только локальным PIN, Google без whitelist | Нет | Нет | Нет |
| Активный viewer | Чтение | Нет | Нет |
| Активный editor или researcher | Чтение | Да | Нет |
| Активный admin | Чтение | Да | Да |

Нужен настоящий Firebase Authentication с подтверждённым email. Роль в
localStorage, URL или произвольном custom claim прав не даёт. Два владельца из
существующего INITIAL_WHITELIST сохраняют доступ только к defaultProject по
подтверждённым email. Для других проектов нужна отдельная проектная запись.

Whitelist хранится в projects/{projectId}/whitelist под ключом, который создаёт
getWhitelistDocId(email). Правила дополнительно сравнивают полный email:
разные адреса могут получить одинаковый нормализованный ключ. Глобальная
коллекция whitelist остаётся зеркалом и не используется для выдачи прав.

## Просмотр без входа

По явно опубликованной ссылке доступна отдельная версия publicTrees. Она
содержит только умерших: isLiving=false либо указан год/дата смерти с годом.
isLiving=true всегда исключает человека. Неизвестный статус, только старый
год рождения, только место смерти, удалённые записи и будущий год смерти
без явной отметки isLiving=false в публикацию не попадают.

Публичные поля ограничены именем, полом, датами/местами рождения и смерти,
связями между опубликованными умершими. Заметки, биографии, контакты автора,
фотографии, сканы, источники и произвольные поля не публикуются: они могут
содержать сведения о живых. Заголовок публичной версии фиксированный.

Полные sharedTrees остаются приватными, включая старые документы. Публичный
просмотр всегда read-only; старый браузерный PIN не открывает полные данные.
После выхода из Firebase приватная версия в shared viewer сбрасывается.

Публикация сначала закрывает предыдущую версию, затем записывает новую
порциями и открывает её только после успешного завершения. При ошибке версия
остаётся закрытой. Старые версии нельзя читать по угаданному пути. Они пока
остаются в базе; автоматическое удаление прошлых версий не включено.
Изменения приватного дерева попадают в публичную версию при повторной публикации.

## Проверки

Проверки выполнялись на Node.js 24 и Java 17; firebase-tools закреплён на
14.27.0 для совместимости с Java 17. Дальнейшее обновление Firebase CLI требует проверки версии Java.

```sh
bun install --frozen-lockfile
bun run test:firestore
bun run lint
bun run build
```

Тесты используют только локальный emulator и demo-my-root-cuba. Перед запуском
проверяется loopback-адрес FIRESTORE_EMULATOR_HOST. Рабочая конфигурация приложения
в тесты не импортируется. firebase.emulators.json отделён от firebase.json,
который указывает фактическую именованную базу.

В наборе 16 тестов, объединённых здесь в 6 групп:

| Требование / риск | Тесты |
| --- | --- |
| Приватные данные доступны только подтверждённым участникам с соответствующей ролью | anonymous clients; Google/custom claim; 4 server-side role; existing owners — 7 тестов |
| Нельзя самостоятельно выдать права или одобрить заявку | canonical whitelist; own access request — 2 теста |
| Гостям выдаются только публичные умершие, закрытые поля не проходят запись | active public version; private fields/nested payloads — 2 теста |
| Нельзя перезаписать чужую публикацию | another editor / viewer — 1 тест |
| Отозванные, старые и незавершённые публикации закрыты | disabled/superseded; failed public write — 2 теста |
| Фильтрация, родственные связи и границы batch | projection; publication across batches — 2 теста |

Это локальные автоматические проверки правил и сервиса публикации. Вход через
Google в рабочем браузере, текущий состав whitelist и развёрнутые правила на
рабочей базе не проверялись.

## Применение к работающему приложению

1. Проверить Google sign-in для существующих владельцев и доступ к проекту Firebase.
2. Проверить доверенность whitelist: прежние открытые правила позволяли менять его
   посторонним. Непроверенные записи нельзя считать безопасными только из-за наличия
   в базе. Старые записи с произвольными ID администратор должен повторно сохранить
   через управление whitelist, чтобы появились канонические ключи. Автоматической
   миграции и изменений рабочих данных эта правка не выполняет.
3. После отдельного согласования опубликовать правила и обновлённое приложение.
   Сначала правила: до обновления клиента публичные ссылки временно будут закрыты,
   зато старые полные снимки сразу перестанут читаться без разрешения.
4. Войти через Google владельцем и повторно опубликовать нужные ссылки. До этого
   новые публичные проекции для старых ссылок отсутствуют. Проверить ссылку в чистом
   браузере без входа и убедиться, что живых и неизвестного статуса в ответах базы нет.

Подготовленная команда публикации правил, выполнять только после согласования:

```sh
firebase deploy --only firestore:rules --project smiling-spanner-31ttq --config firebase.json
```

Основания для реализации: [Firebase: условия доступа](https://firebase.google.com/docs/firestore/security/rules-conditions),
[правила не фильтруют результат запроса](https://firebase.google.com/docs/firestore/security/rules-query),
[локальные тесты правил](https://firebase.google.com/docs/rules/unit-tests),
[лимиты проверок в batch](https://firebase.google.com/docs/rules/rules-behavior).
