# Согласование локальных корзин

Ветка `fix/cloud-trash-reconciliation` основана на `fix/cloud-download-read-only` (`2e76480`). Работа выполнялась локально 25 ноября 2026.

Согласование использует два подтверждения сервера: отсутствие ID среди отметок удаления и наличие активного документа этой персоны. После этого запись возвращается из устаревшей локальной корзины без обратной отправки на сервер. Пустой ответ по персоне не доказывает удаление. Подтверждённая отметка удаления сохраняет локальную копию в корзине, если она ещё была активна. Новые неподтверждённые локальные удаления и восстановления имеют приоритет над старыми ответами.

Локальные изменения согласования сохраняются в IndexedDB и не создают dirty-операции. В manual изменения приходят при явной загрузке; в auto — из подтверждённых подписок. Переключение режима очищает прошлые подтверждения и пересоздаёт подписки. Подписка персон получает весь список, включая пустой, и не использует прежнее ограничение 400 записей. Снимки из кэша и с ожидающими записями не считаются подтверждением сервера.

Ручная замена данных блокируется, если имеются неотправленные удаления/восстановления, в том числе появившиеся во время чтения. Это сохраняет записи, необходимые для повторной отправки.

## Potential defects & technical risks

- Одновременные противоположные действия разных клиентов над одним ID всё ещё требуют согласованной политики версий. Сценарий стенда: A восстанавливает P, B одновременно удаляет P; проверить итоговые документ, отметку и обе корзины. Эти операции не являются одной транзакцией.
- Сохранение копии при получении чужой отметки удаления является консервативным инженерным решением. Протокол пока не различает облачное мягкое и окончательное удаление. Для глобального уничтожения копий нужна отдельная явная политика.
- Списки с данными персон и отметками поступают отдельными подписками. При отсутствии одного из подтверждений восстановление откладывается; отсутствие записи не используется как доказательство удаления. Сценарий стенда: задержать каждую подписку по очереди и проверить отсутствие потери локальных данных.
- Полная подписка персон увеличивает чтение при первом подключении большого дерева. Прежнее отсечение списка на 400 элементах не обеспечивало полноты; дальше нужно измерить локальную обработку больших наборов.
- Перед выпуском проверить с двумя отдельными профилями: удаление на A → загрузка B → восстановление на B → отправка B → обновление A; затем повторить с отключённой сетью и ожидающим локальным удалением на A. Рабочий Firebase при разработке не использовался.
